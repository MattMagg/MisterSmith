# Fault-Tolerance Patterns for LLM-Powered Agents

This report surveys state‑of‑the‑art fault‐tolerance and resilience patterns for building supervised, self‑healing multi‐agent systems that call LLM APIs. We draw on Erlang/OTP literature, distributed systems, chaos engineering, and critical‑infrastructure resilience to cover each dimension. For each topic we summarize existing techniques (with citations), discuss how they map to a Rust+OTP+NATS architecture, and assess complexity and impact.

## 1. Supervising External Service Calls in OTP

**State of the art:** In Erlang/OTP design, one typically *does not* tightly couple transient HTTP calls to long‑lived supervisors. Transient tasks (e.g. one‐off web requests or data fetches) are often run as unsupervised Tasks or under a `restart: temporary` supervisor [3]. The rationale is “let it crash” applies, but restarting a transient process makes little sense because its context is gone【3†L459-L464】. Instead, OTP advises that processes relying on external services should *expect* failures and handle them gracefully【14†L493-L500】. For example, a GenServer calling a remote API might catch errors and return `{error, Reason}` to callers, rather than crash itself. 

**Key techniques:**  Common OTP patterns include:
- **Decoupling calls via Tasks:** Spawn a lightweight Task (or child worker) to make the HTTP request, rather than blocking a long-lived GenServer. The supervisor can watch the Task but typically configure it as `temporary` (so failure is logged but not endlessly restarted). A GenServer might `trap_exit` and supervise its own workers【9†L115-L123】. Alternatively, use a `Task.Supervisor` to run calls with monitored links and custom timeouts. 
- **Timeout management:** Use explicit timeouts on calls (e.g. `gen_server:call(server, Msg, Timeout)`) or `receive … after` in workers, so that an unresponsive service triggers an error rather than hanging indefinitely. Setting a read/connect timeout on the HTTP client (e.g. 30s) and handling it as a failure is common. GenServers should not block on external calls; instead, spawn a child or offload to avoid stalling the main loop.
- **Manager‑worker pattern:** If we expect repeated failures, one can insert a *manager* process above a temporary supervisor. The *manager* monitors failure counts and implements backoff or circuit-breaker logic. For example, the Adopting Erlang “manager-worker” pattern has a supervisor (with strategy and restart limits) under a higher-level manager. The manager checks if a subtree (making external calls) has failed too often; if so, it delays or stops restarting it and optionally triggers exponential backoff or queries a service registry【14†L567-L576】. This lets you treat the manager as a brain around the supervisor to implement non-trivial retry logic like exponential backoff, circuit-breaker untrip, or admin override【14†L567-L576】.
- **Circuit breakers & backoff:** Treat each provider call with a circuit-breaker or rate-limiter. OTP does not mandate a built-in circuit process, but libraries (and design patterns) exist. One could run a CircuitBreaker (Phase 2) as a supervised GenServer that tracks failures and trips a breaker. If tripped, calls immediately fail (and can trigger fallback logic), rather than the calling process simply crashing. This isolates “poison pill” scenarios: if a restart would just immediately crash again (because the service is still down or rate-limited), a circuit-breaker can open and force the caller to wait.
- **Graceful failure:** OTP encourages designing the client so external failure yields a controlled error, not a crash of the whole subtree【14†L493-L500】. For example, if a database or API is unreachable, a GenServer can return `{error, not_connected}` and retry later, rather than supervising that it must always be up【14†L482-L490】. The callers decide tolerable failure levels (e.g. queue the request, drop it, or report degraded functionality)【14†L493-L502】.

**Rust+OTP applicability:** These patterns transfer well. In Rust with OTP-style supervision (e.g. via an Erlang-inspired library), one would spawn short-lived async tasks (futures) for HTTP calls, monitor them, and not supervise them as permanent children. A long-lived “caller” actor would supervise only its persistent state machines, and spawn tasks for each external call. Circuit breakers and backoff policies from Phase 2 integrate naturally: the caller actor can use the CircuitBreaker library or a dedicated breaker actor before making the HTTP request. The manager-worker pattern can be implemented as an OTP-style subtree: a temporary-sup supervisor and a manager actor controlling it.
   
**Complexity:** Moderate. Implementing basic restart/trap is straightforward. A full manager component with exponential backoff or admin interface adds logic (but much can be library- or configuration-driven). Tracking timeouts and using circuit breakers is common practice (Phase 2) with modest complexity.  

**Impact:** Very high. Proper supervision of external calls prevents “crash loops” and unbounded resource use. Instead of letting an external outage bring down the app, well-placed supervisors and breakers ensure the system degrades gracefully and retries intelligently. This yields far higher availability than a naive “call and crash on error” approach.

## 2. LLM‑Specific Failure Modes

LLM APIs introduce unique failure modes beyond typical HTTP services. We categorize them and cite handling guidance:

- **Rate limiting (HTTP 429):** Almost every LLM provider enforces RPM/TPM quotas. A 429 response (often with `Retry-After` header) indicates a transient overload. This is usually recoverable: clients should retry with backoff (with jitter)【16†L79-L87】【26†L60-L68】. For OTP, this means catching 429 and delaying/scheduling a retry (or handing off to a backoff process) rather than crashing. We treat it as *transient* (circuit stays closed).
  
- **Timeouts and network errors:** Timeouts (connect/read) or DNS failures are transient. They should trigger retry with backoff. OTP nodes can use the φ-accrual detector on latency to flag unusually slow responses; or rely on HTTP client timeouts to produce errors. If streaming data had already partially gone to a user, one must avoid duplicating outputs on retry. In general, treat timeouts as *transient*【26†L80-L86】.

- **5xx server errors:** Providers do occasionally suffer internal errors (500, 502, 503, 504). Like timeouts, these are considered transient. Retry with exponential backoff (and possibly switch to a fallback model/provider if retries fail). Hammering repeatedly is counterproductive; add jitter【16†L119-L128】【26†L88-L94】.

- **Invalid request (400-family) – client fault:** This includes malformed inputs, invalid parameters, or context-window overflow. For example, `context_length_exceeded` is common when the chat history is too long【26†L98-L104】. These are non-retryable without change: e.g. trim the prompt or abort the request. OTP actors encountering a 400 should not crash but return an error to the workflow (or adapt the input). Context overflow *can* be programmatically fixed by truncating history and retrying once. Otherwise, treat 400s as *structural errors* requiring input correction【26†L98-L104】.

- **Model not available / Deprecated (404 or invalid model):** If an API reports that a model is unavailable or deprecated, retrying the same request is pointless. This is a structural change: the system must route around it. Strategies include: switch to a different model (fallback chain), update configuration, or surface an error to ops. We should treat this as a *non-transient failure* for that model instance; supervisors shouldn’t endlessly restart the same actor hoping it fixes itself.

- **Authentication/Quota exhaustion (401/403/402):** E.g. invalid API key (401/403) or “payment required” (402) when quota is consumed. These are not transient. On auth errors, the actor should log and crash (so an operator notices). On quota exhaustion, one can only wait for refill or switch accounts; treat as terminal for that request (perhaps route to another provider if available). 

- **Content filtering / rejection:** Providers may refuse to process or return content that triggers safety filters. This typically comes as a 400/403 with a special error. It is not fixed by retrying with the same prompt. One could modify or red-team the prompt, but that’s application logic. OTP supervision should treat a filtering rejection as a final failure for that request, possibly logging or dead‑lettering it.

- **Partial streaming failures / stale connections:** Streaming APIs (server-sent events) can be interrupted. If the connection drops mid-response, the output is incomplete. One pattern is to detect such an error (e.g. by a missed keepalive or a read timeout) and restart the call (maybe using a `restart::transient` child). Since no work was committed, retrying is valid. However, if part of the result was consumed externally, the system must avoid double-output; it may buffer and only commit state after full completion. Treat partial streams as transient network errors and retry from scratch, with a circuit-breaker to avoid endless loops on a flakey stream.

- **Hallucination loops:** This is not an HTTP error but when a model becomes stuck in degenerate outputs (e.g. repeating itself). Detecting this requires observing content (e.g. maximum tokens or repetition heuristics). In OTP terms, a worker could kill itself if it sees nonsensical output, triggering a supervised retry (e.g. via a changed prompt or different model). Since hallucinations are semantic failures, they may require external logic or simplified fallback prompts. We classify these as *logical failures* within the agent, not handled by standard HTTP fault tolerance.

- **Context window overflow:** When the conversation grows beyond the model’s limit, the API returns a context overflow error (often 400 with code like `context_length_exceeded`)【26†L102-L110】. This is semi-structural: the actor should catch this, truncate or summarize history, and retry. It’s not fixed by waiting, but is recoverable with adaptation.

**Applicability to OTP supervision:** Each failure type implies different handling. Transients (429, 5xx, timeouts, partial streams) should be retried under supervision (or cause the actor to crash and be restarted by a supervisor). Permanent failures (4xx invalid, auth, model not found) should usually be logged and not retried blindly. Using OTP’s restart policies, one might mark an actor handling a bad request as `temporary` so it dies without restart. Circuit breakers (Phase 2) wrap calls so that repeated failures prevent futile restarts. Fallback strategies (see below) can be triggered when one model consistently fails (shift to next in chain). 

**Complexity:** Implementing per-error logic adds code (HTTP client error parsing and branching). However, many cases are binary: retry/backoff vs fail. Libraries like those described by GrizzlyPeak provide reusable wrappers. In Rust, one would parse response codes and either return an Err (so the supervisor restarts the call) or a special error to indicate “do not restart”.

**Expected impact:** High. Recognizing which LLM errors to retry versus fail prevents wasted retries and infinite loops. It also enables graceful fallback (e.g. using a cheaper model when GPT-4 is rate-limited). Without such logic, applications either crash on the first error or endlessly hammer a failed model, both unacceptable in production.

## 3. Self‑Healing Agent Topologies

**State of the art:** In distributed systems and self‑adaptive networks, dynamic reconfiguration is key to resilience. Research on *self‑healing networks* (e.g. SDN or mesh networks) shows controllers automatically reroute traffic around failures and update topology as nodes appear/disappear. In LLM agent systems, the analogous need is for the supervision tree to adapt to failing components. Recent MAS (multi-agent systems) research (MAS‑FIRE, 2026) finds that *iterative, closed-loop architectures* (with feedback) recover from over 40% of faults that break linear workflows【35†L148-L152】. This implies that agent teams designed with feedback (critic agents, repeated planning) are inherently more fault-tolerant than one-shot pipelines.

**Key techniques:** 
- **Dynamic failover:** If one LLM provider consistently fails (e.g. due to rate limits or outages), the system should automatically shift tasks to an alternative (fallback) provider without manual reconfiguration. This can be implemented by monitoring each provider’s health (error rate, latency) and maintaining a prioritized list of providers for each task type. In OTP terms, a supervisor could terminate or pause the failing provider child and spawn a new child bound to a different API. Alternatively, a load‑balancing actor can route requests only to healthy providers. 
- **Adaptive fallback chains:** Instead of a static fallback sequence, one could adapt the chain based on history. E.g. if Provider A failed 80% of requests recently, deprioritize it for new tasks. Such feedback loops can be implemented via a health monitor (Phase 3) feeding state into a decision actor.
- **Topology healing from networks:** In SDN, the controller updates routes; in P2P meshes, nodes self-organize around outages. For agent graphs, this suggests supervisors might rewire workflows: e.g. if a Planner agent fails, a Critic could become interim Planner, or vice versa. Such dynamic graph edits are complex but possible: OTP supervisors can `terminate` and `start_child` subtrees at runtime.
- **Chaos experiments / learning:** Some approaches use fault injection (chaos engineering) to learn and adapt. For example, Netflix’s Chaos Monkey deliberately kills nodes to test recovery. In a MAS, one could periodically simulate an agent outage and record how remaining agents compensate. Over time, one could adjust supervisor strategies (e.g. raising a circuit breaker threshold or adjusting backoff) based on observed outcomes.
- **Reconfiguration management:** OTP’s hot code upgrade or release tools could be leveraged: e.g. a management process could shut down a “subtree” of failed providers and bring up an updated one. The Adopting Erlang manager-worker pattern (see section 1) is an example: the manager can consult an external registry and restart missing subtrees【14†L575-L583】.

**Applicability to Rust+OTP+NATS:** With NATS providing a global state or key-value (JetStream/KV store), agents on different nodes can publish health status (heartbeat latency, error counts) to a stream. Supervisors on each node can subscribe to NATS topics for coordinated failover decisions. For example, all instances of Provider A could publish their health; if many failures occur, all supervisors back off that provider. Restart strategies (one_for_one) allow individual agents to be restarted, while Node-level supervisors could use `rest_for_one` or `one_for_all` when restructuring.

**Complexity:** High. Truly adaptive topology (rewiring agent graphs) is sophisticated. Simpler dynamic failover (switch providers, adjust weights) is medium complexity: it requires health tracking and conditional logic, but can be implemented by combining existing components (Phi detector, CircuitBreaker) with a “balancer” actor. Fully self-adjusting architectures (learning from chaos tests) border on research, but even static fallback logic informed by monitoring yields big gains.

**Expected impact:** Very high if done well. Dynamic failover ensures the system routes around failures without human intervention, greatly improving availability. A MAS that can reroute tasks and recover subflows will complete more workflows even under partial outages. The MAS-FIRE results imply that adding feedback loops (closed‑loop agent communication) can prevent many failures in the first place【35†L148-L152】.

## 4. Graceful Degradation in Multi-Agent Systems

**State of the art:**  Critical systems (aviation, medicine) always plan for degraded modes. For example, fly-by-wire aircraft automatically switch to “backup flight laws” with reduced control authority if sensors fail; HUD displays simplify if one system crashes. In software, the *bulkhead pattern* isolates components so one failure doesn’t sink the ship【58†L86-L94】. Recent AI-system writings emphasize graceful degradation: an agent system should continue serving core functions even when some models fail【39†L1244-L1250】.

**Key techniques:**
- **Bulkhead isolation:** Partition the agent system so failures are contained. For example, run expensive GPT-4 calls in a separate thread-pool or actor pool from cheaper GPT-3.5 calls. If the expensive pool is rate-limited, the cheap pool can still operate【58†L86-L94】. In OTP terms, this means separate supervisors/workers for different providers or roles. Bulkheads ensure that, say, one Executor failing doesn’t freeze the Planner or other Executors.
- **Capability degradation:** Define service levels. E.g., **full** mode uses all agents and the best models; **degraded** mode uses fewer examples or a smaller model; **minimal** mode might rely on templates or cached answers. If the preferred Planner model is down, the Planner actor can switch to a simpler planning routine or scrap certain sub-tasks. Likewise, Executors can fallback to a faster, cheaper model when the high-end one is unavailable. This is akin to aviation’s degraded HUD – still flyable, just with fewer features.
- **Fallback chains as degraded strategy:** We saw earlier fallback chains of models. That is a form of graceful degradation: if primary GPT-4 is throttled, fall back to GPT-3.5. Similarly, if a visionary Critic agent (highly specialized) is offline, let a general-purpose agent fill in partially.
- **Resource shedding:** If resource limits are hit (e.g. token budget or latency targets), the system can shed non-critical tasks. For instance, skip optional Critic steps or delay less urgent queries. Bulkheads are one form: limit concurrency so a flood of requests to one agent cannot deplete the whole system.
- **Status communication:** Degraded systems communicate their status. An agent network might broadcast “degraded mode: switching to simpler plan” so that downstream agents expect simpler inputs. This parallels user notices in degraded mode (a website showing minimal UI when backend is slow). 
- **Graceful degrade patterns:** Just as PraisonAI notes, test every degradation path and provide fallbacks【39†L1244-L1250】. In practice, design each agent to know its “reduced mode”: e.g. Planner can skip optional branches, Executor can use cached completions, etc.

**Applicability to Rust+OTP+NATS:** Separate threads or actors for different functions/providers implement bulkheads naturally. Supervisors enforce these partitions. Fallback-chains are already part of design (Phase 9), so an executor could simply try a cheaper model actor if the expensive one fails a health check. NATS can convey global “mode” (e.g. an “all-systems degrade” flag) so agents can uniformly drop to a safe mode. 

**Complexity:** Moderate to high. Designing degraded behavior (especially for complex agents) requires upfront work (e.g. building simpler fallback logic). Bulkhead isolation is straightforward at the infrastructure level. Overall, planning for degraded modes adds development effort but pays off in reliability.

**Expected impact:** High. Graceful degradation means the system never fully stops for non‑critical failures. At minimum, users or orchestrating systems get partial results instead of total failure. This often distinguishes a resilient system from a brittle one. As noted, bulkhead design “ensures core user flow stays fast” even if some services slow or fail【58†L124-L129】.

## 5. Checkpoint and Recovery for Long-Running Workflows

**State of the art:** Modern LLM workflow frameworks increasingly incorporate checkpointing. LangGraph (LangChain’s workflow library) provides *time-travel debugging*: it checkpoints state at each node, letting one resume from any prior point【44†L99-L108】【46†L169-L173】. In other words, each multi-turn agent interaction is logged so the system can roll back or replay steps. This is akin to event-sourcing: each decision (input/state → LLM output) is recorded. In other domains, database patterns like write-ahead logs, savepoints, or even two-phase commit have analogues in workflow state logs.

**Key techniques:** 
- **State snapshots:** After each agent step or tool call, serialize the conversation state and relevant context (variables, embeddings, etc.) to a durable store. This could be JSON blobs in a database or log. LangGraph’s checkpoint ID exactly captures “state before/after each node”【44†L99-L108】. With this, a failing workflow can restart from the last snapshot without rerunning earlier steps.
- **Append-only logs:** Treat the agent workflow like a transaction log. Every message or intermediate result is an event appended to a log (e.g. Kafka, NATS JetStream). The current state is the sequence of events so far. On failure, rehydrate state by replaying the log up to the last good event. JetStream can serve as this durable log – since it supports replay【59†L78-L86】, each agent action could publish its result to a stream. A checkpoint is just an offset in the stream.
- **Savepoints and branching:** Mark savepoints at key milestones (e.g. after each agent turn). Allow branching: you might resume from a savepoint and alter inputs (exploiting non-determinism), as LangGraph’s time-travel does【44†L99-L108】. This means recording enough metadata (thread ID, checkpoint ID) to fork execution. 
- **Crash recovery:** If a multi-step process fails mid-way, the supervisor can capture the failure, consult the last checkpoint, and restart the necessary child from that point. For example, if an Executor calling a model crashes after partial output, its parent can catch the exit, discard the corrupted state, and invoke the model again with the saved input.
- **Two-phase commit analogy:** If an agent workflow involves multiple sub-requests that must all succeed (e.g. updating two external databases), one can use a saga or two-phase-like protocol: prepare all steps (checkpoint state) then commit. If any sub-step fails irrecoverably, abort and maybe roll back others. In practice, this is complex with LLMs, but conceptually, the system could record “pending actions” and only finalize state when all succeed (e.g. only append to the conversation log on final success).
- **Durable storage:** Use JetStream or a KV store for checkpoints. JetStream streams are append-only and replicated, so writing each agent response to a stream makes it recoverable if a process or node dies【59†L78-L86】. The state of each conversation can be reconstructed by reading its stream up to the current position.

**Applicability to Rust+OTP+NATS:** Very applicable. Each agent actor can write its intermediate state to a JetStream stream or KV store (both are supported in NATS). The actor’s process state is just a cache; real durability comes from the stream. On startup, an actor can read its last checkpoint from JetStream and continue. LangGraph’s approach shows it’s production‑ready: the state is JSON and indexed by checkpoint IDs【44†L99-L108】. In Rust, one might use Serde JSON and NATS client libraries to append and read state.

**Complexity:** Medium to high. Designing state schemas and ensuring all relevant data is checkpointed is work. Writing to JetStream/DB after every step adds I/O overhead. Implementing replay logic also takes effort. However, frameworks (LangGraph, workflow engines) already do this, so one can leverage existing patterns. 

**Expected impact:** Very high for reliability. Checkpointing avoids wasted work and lost data. If an agent or host crashes, you don’t have to restart the conversation from scratch. It also provides an audit trail (as LangGraph emphasizes)【46†L169-L173】. In critical applications, having a “flight recorder” for agent decisions means failures can be recovered with no silent data loss. 

## 6. Provider Health Tracking and Predictive Failure Detection

**State of the art:** Traditional systems rely on reactive breakers (trip after failures) and simple heartbeats (phi accrual detectors【49†L62-L66】). Some advanced systems add predictive analytics: e.g. AWS uses CloudWatch anomaly detection on metrics, or can forecast resource needs for auto-scaling【59†L78-L86】 (though not exactly failure prediction). Research on ML for failure prediction (predicting node crashes from metrics) exists but is not yet widely deployed for LLM services.

**Key techniques:** 
- **Extended phi accrual:** Mister Smith’s phi detector watches inter-arrival times. Similarly, one can treat LLM API **response latencies** as “heartbeats.” Track the distribution of response times (p50/p95/p99). If latencies start increasing or vary wildly, raise a suspicion score. For example, if GPT-4 normally responds in ~1s but now has 10s tails, begin throttling it. This is an adaptation of phi accrual: compute φ(t) = -log10(Prob(latency > t)), and trip when φ exceeds a threshold. 
- **Per-provider metrics:** Continuously track each provider’s **error rate** (fraction of requests that return errors or 429), **latency percentiles**, **rate limit utilization** (current tokens/min vs cap), and **token consumption rate**. A health-monitor actor can aggregate these. If error rate spikes or tokens burn too fast, preemptively pause the provider before it fully blocks.
- **Predictive models:** Feed historical metrics into a simple predictor (e.g. an exponentially weighted moving average of errors). If errors show an upward trend, temporarily offload traffic. In cloud ops, anomaly detection tools (time-series algorithms) can flag upcoming instability. In LLM context, one might train a lightweight model on past outages to predict when GPT-4 will hit a limit (e.g. based on time of day).
- **External signals:** Some providers expose status pages or webhooks. An agent could subscribe to a provider’s status RSS or metrics if available. When the provider issues warnings (e.g. “Scheduled maintenance at 3pm”), supervisors can proactively shift to alternatives.
- **Integration with circuit breakers:** Instead of only breaking after N failures, combine with health signals. For example, a breaker could open not only on count of errors but also if latency > threshold for long.
- **Cross-provider correlation:** If multiple customers see growing errors, escalate. If only this system sees issues, maybe it’s an internal problem (e.g. network or credentials).

**Applicability to Rust+OTP+NATS:** Use NATS for distributed health state: each node’s provider-actor publishes heartbeat (timestamp and status). A global aggregator (or local decision based on global trends) can mark providers healthy/unhealthy. The phi-detector module (Phase 3) could be applied directly to LLM response times. The existing HealthMonitor (Phase 2) can track things like p99 latency and send alerts. In practice, one might adapt Erlang’s `heart` or OTP’s `amplify` detectors for use on RPC response times.

**Complexity:** Medium. It requires metric collection and some statistical logic, but no novel infrastructure. Existing monitoring libraries (Prometheus, Graphite) could integrate via NATS for visualization/alerts. Implementing φ formula and threshold crossing is relatively straightforward.

**Expected impact:** Moderate to high. Reactive breakers alone often act too late (after failures happen). Predictive detection can soften failures: switching providers *before* a hard outage, avoiding request storms at dawn of limits. This preemptive strategy can significantly reduce user‑visible errors. It essentially turns occasional outages into smoother degradations.

## 7. Supervision Strategies for Agent Teams

**State of the art:** Erlang’s supervisors offer fixed strategies: `one_for_one`, `rest_for_one`, `one_for_all`【13†L143-L152】【13†L153-L159】. For a team of agents (e.g. Planner + several Executors + Critic), the ideal restart policy depends on dependencies. Industry has not standardized multi-agent restart beyond these primitives, but guidelines are clear:
- **One-for-one (independent agents):** If agents are loosely coupled (e.g. each Executor handles a separate task), use one_for_one so only the failed agent restarts. This minimizes blast radius.
- **Rest-for-one (linear dependency):** If agents have an order (e.g. Critic depends on all Executors), use rest_for_one: if an agent dies, all agents started after it in the supervisor list are restarted. For example, if Planner is first and Executors next, a Planner failure would restart Executors too, ensuring consistency.
- **One-for-all (strong coupling):** If any part’s failure corrupts the whole context (unlikely in stateless agents), use one_for_all: any crash restarts the entire group. This is heavy and used only when partial state would be inconsistent.

**Key techniques:** 
- **Role-aware restarts:** While OTP doesn’t natively know “Planner vs Executor”, one can arrange the supervision tree so critical roles are before less critical ones. For instance, under a rest_for_one supervisor, list the Planner first, then Executors, then Critic. If an Executor fails, only later children (Critic) restart; if Planner fails, all restart.
- **Escalation logic:** We may implement custom behavior in the manager (as in section 1) to treat roles differently. E.g. if Planner (central coordinator) fails repeatedly, escalate to application-level recovery (maybe kill and restart the whole workflow tree).
- **Quorum-based recovery (research idea):** In distributed computation, if some agents are replicas, one could require a majority to be alive before proceeding. Though not standard in OTP, one could implement a consensus actor that waits for k of n results. This is more relevant if agents are parallel workers (like Kubernetes deployments with PodAntiAffinity).
- **Hybrid strategies:** Use multiple supervisors. For example, have one supervisor for all Executors (`one_for_one` or `rest_for_one` among them) under a higher supervisor with the Planner. Then the Planner is a sibling of that subtree. If an Executor fails, its own sub-supervisor restarts it; if the whole subtree fails repeatedly, the super-supervisor may restart both subtree and Planner.

**Applicability to Rust+OTP:** The same supervisor semantics apply. When designing actor supervisors in Rust, you’d choose the strategy that best encodes dependencies. Since Mister Smith already supports one_for_all, etc., one would use rest_for_one for sequences. Role awareness can be achieved by naming children and writing a custom rule: e.g. if an “Executor” role actor fails, restart only it; if “Planner” fails, trigger a larger restart (possibly by having the Planner under its own supervisor).

**Complexity:** Low to moderate. Using built-in supervisor strategies is straightforward. Adding custom escalation (like distinguishing roles) adds some code but not much beyond supervisor configuration. 

**Expected impact:** Moderate. Proper restart strategy ensures we don’t kill unaffected agents unnecessarily. It helps avoid replaying already-computed results. For example, restarting only the failed Executor and not the whole pipeline saves time. More nuanced strategies (like partial restarts or consensus) can slightly improve availability at the cost of complexity. But even just choosing rest_for_one instead of one_for_all reduces wasted work on Planner failures.

## 8. Testing Fault Tolerance

**State of the art:** Testing resilience combines unit, integration, and chaos tests. Erlang/OTP teams often use **Common Test** and **PropEr/QuickCheck** for OTP invariants, and tools like **Supertester** (Elixir) provide fault-injection helpers. Chaos engineering (Netflix Chaos Monkey, Gremlin) has popularized live fault injection in production; similarly, staged chaos tests (e.g. by killing processes randomly) are used to validate supervision logic.

**Key techniques:** 
- **Supervised-failure tests:** Write tests that explicitly crash a supervised child and assert the supervisor restarts it correctly. For example, tools like *Supertester.OTPHelpers* allow simulating a GenServer crash and checking recovery【67†L279-L288】. They can also inject faults into supervision trees.【68†L37-L40】
- **Chaos testing:** Use scripted fault injection (in dev or staging) to kill random agents or simulate provider failures. Supertester’s `chaos_kill_children` randomly terminates children under a supervisor, checking that the supervisor stays alive and children restart【68†L37-L40】【68†L47-L52】. Similarly, one can simulate HTTP failures (e.g. by pointing to a mock server that returns errors or shuts down mid-stream) to ensure the actor handles it as expected.
- **Property-based testing:** Tools like QuickCheck or PropEr can assert generic properties (e.g. “no matter which child crashes, the application eventually stabilizes”) by randomly generating failure scenarios. This ensures supervision invariants (like “system never loses more than N pending tasks”) hold.
- **Chaos engineering in distributed setting:** Inject network partitions between agent nodes, or spike latency. Amazon’s “chaos game days” concept applies: schedule chaos runs where LLM providers are throttled or black‑holed, and verify fallback paths engage properly.
- **Performance/testing harness:** Use Supertester’s `wait_for_process_restart`, `assert_supervision_tree_structure`, etc. to programmatically verify that after failures, the system arrives in a healthy state【67†L242-L250】【67†L321-L330】. Also test concurrency (simulate many simultaneous LLM requests to ensure thread-safety of health metrics).

**Applicability to Rust+OTP:** The same principles hold. We can write tests that stop or panic an actor, then assert the supervisor restarts it. A Rust version of Supertester might be built on top of the actor framework (by catching actor deaths). For chaos, we can use local tools (or Kubernetes jobs) to terminate processes. For HTTP failures, use injected fault servers or mock providers that exhibit 429, timeouts, partial streams, etc. Property testing is language-agnostic and can be done in Rust with tools like proptest.

**Complexity:** Moderate. Building a robust test suite with fault injection takes effort, but is crucial. Frameworks help automate it. Once set up, these tests are repeatable (not random) and can be integrated into CI. Chaos engineering in staging requires infrastructure, but pays off in confidence.

**Expected impact:** High. Without testing, subtle failures in supervision logic can hide until production. Chaotic tests catch regression early. For instance, verifying that killing one Executor doesn’t crash the workflow avoids real user downtime. As one Supertester guide notes, ensuring “system recovers from chaos” is a best practice【68†L49-L57】.

## Synthesis and Recommendations

**Integrated Architecture:** Based on the above, an optimal fault-tolerant design for Mister Smith’s Rust agents with OTP supervision and NATS is as follows:

- **Supervision tree design:** Structure supervisors to reflect dependencies. For example, have one_for_one supervisors for pools of homogeneous workers (e.g. a pool of Executors), and rest_for_one where there is order (Planner → Executors → Critic). Use `restart: temporary` for transient caller processes to avoid fruitless restarts【3†L459-L464】. Insert a *manager* process above any subtree that makes external LLM calls: the manager monitors failure frequency and either lets the subtree restart or triggers exponential backoff/disable【14†L567-L576】.
  
- **Fault detection (Phase 2-3):** Wrap all LLM HTTP calls with a CircuitBreaker and timeouts. Use the PhiAccrual detector to monitor response-time drift per provider. Track p50/p95/p99 latency and error rates via a HealthMonitor that publishes to NATS. Feed these signals into a provider health registry (a NATS Key-Value or JetStream stream). If a provider’s health degrades (e.g. too many 429s or latency spiking), preemptively trip its circuit or mark it as offline so that new tasks go to a fallback model【26†L60-L68】【26†L115-L120】.

- **Failure-handling per mode:** Implement specialized handlers for LLM error types as identified. For 429/5xx: automatically retry (with backoff) and log metrics. For 400 or content-filter: abort that request (do not restart the actor). On model-deprecation or context-exceeded: adjust input or switch model and retry once. Use fallback chains: if primary model fails (e.g. after 2 retries), try the next model/provider in the chain【28†L19-L27】【28†L49-L58】.

- **Fallback and degradation:** Define fallback models/providers in priority order. The agent workflow should consult this chain – if one fails, automatically invoke the next (maintaining conversation context). Use simpler prompts or cached responses for low-priority queries if no models are available. Implement bulkheads by giving critical tasks their own supervised pools and resource limits, so one slow API doesn’t freeze the whole system【58†L86-L94】.

- **Checkpointing:** After each agent step, publish its state to JetStream (append-only). This provides a durable log of conversation state. On actor restart (post-crash or planned recovery), resume from the last checkpoint (retrieved from the stream) rather than starting over【44†L99-L108】【46†L169-L173】. This also enables “time-travel” debugging if needed.

- **Runtime coordination via NATS:** Use JetStream streams or KV stores to broadcast global health and config. For example, a “global outage” flag or provider status topics allow all agents to switch modes consistently. Also use NATS for heartbeats: a central watchdog could subscribe to all agent pings via JetStream to detect silent stalls.

- **Resilience practices:** Incorporate chaos tests regularly (during development) to validate failover. For instance, simulate the primary LLM dying mid-request and verify fallback executes. Employ property tests to ensure invariants (e.g. “every request either succeeds or hits dead-letter queue, and never loops forever”).

**Expected benefits:** This architecture is far more reliable than naive retry-and-crash. With isolated supervision, failed agents auto-restart without disturbing others. Circuit breakers prevent incessant retries against a down provider. Health signals allow proactive re-routing. Bulkheads ensure critical functions remain alive. Checkpointing guards against lost work. Graceful degradation and fallback maintain partial service instead of total failure. Overall, the system can handle LLM quirks (rate limits, timeouts, etc.) and downstream failures without silent data loss or infinite loops, meeting high reliability requirements.
