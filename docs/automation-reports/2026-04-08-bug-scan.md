## Credible Bug Candidates

### 1. Direct execution prep misclassifies `inspect` requests as SpecKit work

Why it looks wrong:

- the current Smith-first route recommends `prepare_direct_execution` for tracked execution
- the latest compatibility-surface expansion added substring-based SpecKit detection in
  `build_direct_execution_plan()`
- that matcher includes the bare token `"spec"`, which also matches unrelated words like
  `inspect`

Exact evidence:

- `crates/mister-smith-mcp/src/compatibility.rs`
  - `build_direct_execution_plan()` currently sets `should_use_speckit` through:
    `contains_any(&request_text.to_lowercase(), &["speckit", "packet", "spec", "tasks.md", "task pack"])`
- direct reproduction on current `main`:
  - `prepare_direct_execution(request_text="Inspect recent main history for grounded bugs")`
    returned:
    - `should_use_speckit=true`
    - pending gate `speckit_packet_ready`
    - blocker `SpecKit execution was requested but no tasks.md path could be resolved`
    - `docs_to_read` including `.codex/commands/implement.md` and `.codex/prompts/speckit.implement.md`
  - `prepare_direct_execution(request_text="Tighten Smith routing guards without a linked issue")`
    returned `should_use_speckit=false` under the same no-issue context
- the positive-path regression tests still pass, so the bug is not a broad tool failure:
  - `cargo test -p mister-smith-mcp compatibility_server_lists_plain_tool_names -- --nocapture`
  - `cargo test -p mister-smith-mcp route_workflow_request_routes_packet_authoring_requests_to_spec_authoring -- --nocapture`

Likely impact:

- ordinary investigation or audit requests can be blocked by a false SpecKit gate
- callers can get the wrong next-step guidance and the wrong docs-to-read bundle
- Smith control-plane prep becomes less trustworthy for non-packet execution requests
