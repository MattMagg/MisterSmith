## Credible Bug Candidates

### 1. Session-shell direct-store fallback bypasses HTTP status failures

Why it looks wrong:

- packet-030 added direct durable-store fallback so the CLI could stay usable when the runtime is
  actually unreachable
- current `main` still falls back on any session HTTP error, including explicit status rejections

Exact evidence:

- [`crates/mister-smith-app/src/conversation.rs`](/tmp/mister-smith-bug-scan-2026-04-06/crates/mister-smith-app/src/conversation.rs#L1457)
  `resolve_last_session_id()` falls back to `list_sessions_direct(1)` whenever
  `list_sessions_http()` is not `Ok(...)`
- [`crates/mister-smith-app/src/conversation.rs`](/tmp/mister-smith-bug-scan-2026-04-06/crates/mister-smith-app/src/conversation.rs#L1474)
  `inspect_session_for_cli()` catches any `Err(err)` from `inspect_session_http()` and then loads
  `inspect_session_direct()` while labeling the result `runtime_unavailable`
- [`crates/mister-smith-app/src/conversation.rs`](/tmp/mister-smith-bug-scan-2026-04-06/crates/mister-smith-app/src/conversation.rs#L1500)
  `update_session_control_for_cli()` catches any HTTP error and writes through
  `update_session_control_direct()`
- [`crates/mister-smith-app/src/conversation.rs`](/tmp/mister-smith-bug-scan-2026-04-06/crates/mister-smith-app/src/conversation.rs#L1515)
  `build_startup_home()` falls back to `list_sessions_direct(limit)` on any `list_sessions_http()`
  error
- [`crates/mister-smith-app/src/main.rs`](/tmp/mister-smith-bug-scan-2026-04-06/crates/mister-smith-app/src/main.rs#L699)
  `/sessions` falls back to `list_sessions_direct(20)` on any `list_sessions_http()` error
- PR `#324` CodeRabbit review explicitly warned about the same unsafe fallback pattern, and the
  merged `main` code still matches that warning

Likely impact:

- a `401`, `403`, `404`, or other server-side rejection can be masked as `runtime_unavailable`
- the CLI can read or mutate retained session state directly when it should surface the HTTP error
- operators get misleading support notices that imply runtime reachability problems rather than the
  real failure

Why it looks wrong:

- the repo carries a detailed `tools:` block that appears intended to shape CodeRabbit behavior
- CodeRabbit warned on PR `#324` that the key is unsupported and ignored
- the unsupported block is still present on current `main`

Exact evidence:

- [`/.coderabbit.yaml`](/tmp/mister-smith-bug-scan-2026-04-06/.coderabbit.yaml#L176)
  still contains the unsupported `tools:` block at lines `176-216`

Likely impact:

- the repo's intended review-tool posture is not the posture CodeRabbit actually enforces
- every affected PR keeps carrying avoidable strict-warning noise on the review surface
