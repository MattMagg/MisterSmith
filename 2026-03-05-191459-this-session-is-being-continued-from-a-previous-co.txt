     crates/mister-smith-agents/src/agent.rs
       #10682           🟣  Implemented AgentRuntime and AgentContext Bridge 
     Layer
         Implemented the Actor-Agent bridge layer identified in research 
     decision R1, solving the ownership model mismatch between the Actor trait 
     (&mut self for state mutation) and the Agent trait (&self with interior 
     mutability). AgentContext provides shared, thread-safe state accessible 
     from multiple call sites: AgentId and AgentType are immutable copies, state
      uses AtomicU8 for lock-free reads (important for registry queries and 
     health checks), restart_count uses AtomicU32 for supervision tree updates, 
     while started_at and health use RwLock for less frequent updates requiring 
     multiple fields. AgentRuntime<M, R> is generic over message and response 
     types, allowing type-safe message passing through the wrapped ActorRef 
     while exposing agent-level operations like stop(), state queries via the 
     watch channel (more up-to-date than the atomic for real-time tracking), and
      wait_for_state() for synchronization. The tell() and ask() methods 
     delegate directly to ActorRef, preserving the fire-and-forget and 
     request-response patterns from Phase 3. The spawn_agent function 
     encapsulates the actor spawning ceremony: creates AgentContext with the 
     provided config, spawns the actor through ActorSystem.spawn_with_handles() 
     (hypothetical extension returning stop_tx and state_rx alongside ActorRef),
      wraps all three handles in AgentRuntime, transitions state to Running, and
      records the startup timestamp for lifecycle tracking. The stop() method 
     sends a graceful shutdown signal via stop_tx, sets state to Stopping, and 
     consumes the sender (Option.take()) to prevent duplicate stop requests. 
     This bridge pattern enables agents to participate in both the actor runtime
      (via ActorRef for message processing) and the orchestration layer (via 
     AgentContext for discovery, health tracking, team membership).

       #10683           🔄  Refactored AgentRuntime to Delegate State Management
      to ActorSystem
         Refactored AgentRuntime implementation to eliminate duplicate state 
     tracking and establish ActorSystem as the single source of truth for actor 
     lifecycle state. Originally, AgentContext maintained its own AtomicU8 state
      field synchronized with ActorCell's state_tx watch channel, creating two 
     copies of the same information. This violated the single responsibility 
     principle and risked inconsistency if updates weren't perfectly 
     synchronized. The refactored design removes this duplication: AgentContext 
     no longer tracks state, and AgentRuntime stores Arc<ActorSystem> to query 
     state on-demand via get_actor_state(). This makes state() an async method 
     (acceptable tradeoff since state queries aren't on hot paths) but 
     guarantees consistency with the actor cell. Similarly, the stop() method 
     now delegates to system.stop_actor() instead of manually sending stop 
     signals via stop_tx, ensuring proper cleanup through the system's shutdown 
     machinery. The spawn_agent function was simplified to match the actual 
     ActorSystem API (spawn() returns only ActorRef, not a tuple with handles), 
     eliminating the hypothetical spawn_with_handles() method. AgentRuntime 
     construction moved inline to spawn_agent since the intermediate constructor
      no longer served a purpose. Added comprehensive unit tests covering the 
     full agent lifecycle: spawning with config validation, ask pattern for 
     request-response, tell pattern for fire-and-forget, graceful stop with 
     liveness verification, and state query consistency. Tests use a minimal 
     TestActor implementing the Actor trait with message counting to verify 
     state mutation across messages. This refactoring reduces code complexity 
     (eliminated 40+ lines), improves maintainability by centralizing state 
     management, and provides test coverage for core agent operations.

     scheduler's need to find qualified workers for assignment. Update methods 
     use DashMap's get_mut for atomic in-place modification without 
     read-modify-write races, enabling the heartbeat monitor to update 
     heartbeat_at timestamps and the health monitor to update health levels 
     concurrently. The test suite validates core operations: registration 
     creates entries retrievable by ID, find_by_type correctly filters by role, 
     find_available_filters verifies the composite predicate excludes Unhealthy 
     and Terminated agents, deregister removes entries cleanly, and 
     update_health demonstrates atomic updates. This registry serves as the 
     foundation for distributed agent discovery (Phase 7 spec references NATS 
     subject subscriptions on agents.> wildcard for cross-node discovery).


     crates/mister-smith-agents/src/messaging.rs
       #10685           🟣  Implemented Messaging Primitives for Inter-Agent 
     Communication
         Implemented messaging primitives providing a clean API for inter-agent 
     communication by wrapping the Transport trait from mister-smith-transport. 
     The four functions cover common messaging patterns: send for 
     fire-and-forget one-way messages (e.g., task assignments, status updates), 
     request for synchronous request-reply workflows (e.g., querying agent 
     state, invoking tools), broadcast for fan-out notifications to multiple 
     agents via NATS wildcard subscriptions (e.g., system-wide announcements), 
     and send_durable for guaranteed delivery semantics through JetStream (e.g.,
      critical task assignments that must survive restarts). The implementation 
     is deliberately thin: each function is a one-liner calling the appropriate 
     Transport method and converting errors. The send_durable function is 
     identical to send in implementation because durability is a transport-layer
      concern—calling code specifies intent, and the actual Transport 
     implementation (NatsTransport with JetStream enabled) handles persistence, 
     acknowledgments, and redelivery. This separation of concerns allows testing
      with InMemoryTransport (no durability) in unit tests while guaranteeing 
     correct behavior in production with JetStream. Error conversion to 
     AgentSystemError::MessageDeliveryFailed provides a consistent error model: 
     application code using these primitives deals with agent-level errors, not 
     transport-level details like connection failures or ack timeouts. The 
     functions accept &dyn Transport for flexibility—callers can use any 
     transport implementation (NATS, HTTP, gRPC) without changing agent code. 
     MessageEnvelope from mister-smith-transport carries correlation IDs, trace 
     IDs, priority, and serialized payloads, providing rich metadata for 
     distributed tracing and message routing. These primitives will be used by 
     AgentRuntime, TaskScheduler, Orchestrator, and Team for all inter-agent 
     communication, establishing a consistent messaging foundation across the 
     agent system.


     crates/mister-smith-agents/src/heartbeat.rs
       #10686  2:37 PM  🟣  Implemented HeartbeatEmitter for Agent Liveness 
     Tracking
         Implemented HeartbeatEmitter providing periodic liveness signals for 
     phi accrual failure detection, as specified in research decision R6. Each 
     agent spawns a HeartbeatEmitter with its AgentId and the heartbeat_interval
      from AgentConfig (defaults: 5s for Worker, 3s for Supervisor, 2s for 
     Monitor). The start method launches a background tokio task that publishes 
     MessageEnvelope-wrapped heartbeat messages to a NATS subject following the 
     naming pattern agents.{id}.heartbeat. The task uses tokio::time::interval 
     for precise periodic ticking regardless of message publish latency, 
     ensuring consistent heartbeat intervals even under load. Each heartbeat 
     contains a JSON payload with agent_id (UUID string) and timestamp (RFC3339 
     format) for time-series analysis and drift detection. The MessageEnvelope 
     builder sets source_agent_id metadata enabling correlation with other 
     messages from the same agent. The tokio::select! multiplexes interval 
     ticking with stop signal monitoring via a watch channel: ticker.tick() 
     triggers heartbeat publish, while stop_rx.changed() checks for shutdown 
     signal. This design ensures graceful termination without blocking interval 
     timers. The stop method sends the stop signal and immediately aborts the 
     task handle, providing both cooperative (signal-based) and forceful (abort)
      shutdown paths. The Drop implementation automatically calls stop, ensuring
      no leaked background tasks when HeartbeatEmitter goes out of scope (e.g., 
     agent crashes or is deregistered). The is_running method exposes task 
     liveness for integration with HealthMonitor. Heartbeat messages flow 
     through NATS to subscribers monitoring the agents.*.heartbeat wildcard 
     pattern, feeding the phi accrual failure detector in the liveness monitor 
     (Phase 2's HealthMonitor with phi > 8.0 threshold ≈ 99.97% confidence of 
     failure). This passive monitoring approach avoids active request-reply 
     probing overhead while providing adaptive failure detection that adjusts to
      network jitter.


     crates/mister-smith-agents/src/scheduler.rs
       #10687           🟣  Implemented Task Scheduler with State Machine and 
     Pluggable Decomposition
         Implemented task scheduling infrastructure with state machine, 
     hierarchical decomposition support, and concurrent task tracking via 
     DashMap. TaskAssignment entity mirrors the data model specification (14 
     fields) capturing task identity (task_id, task_type), scheduling metadata 
     (priority u8 with 0=highest following MessagePriority pattern, deadline for
      time-bounded execution), execution payloads (input/output as JSON for 
     flexibility), lifecycle tracking (state enum with 7 values, assigned_to 
     agent, timestamps), decomposition hierarchy (parent_task_id for subtask 
     relationships), team context (team_id for multi-agent orchestration), and 
     deduplication (message_id for idempotent processing). The priority field 
     defaults to 128 (middle of u8 range) matching the research decision to 
     support priority-ordered mailboxes (BinaryHeap with lower values = higher 
     priority). The state machine enforces valid transitions: submit creates 
     Pending tasks, assign validates Pending→Assigned and records 
     agent+timestamp, start validates Assigned→Running, complete validates 
     Running→Completed and records output+timestamp, fail transitions from any 
     state to Failed with error message, timeout marks TimedOut, and reset 
     returns to Pending for retry (clears assigned_to, assigned_at, 
     error_message). TaskDecomposer and ResultAggregator traits provide 
     extension points for hierarchical task processing: decompose breaks complex
      tasks into subtasks (with parent_task_id linking), aggregate combines 
     subtask results following the parent-child graph. Default implementations 
     (IdentityDecomposer returns task unchanged, ArrayAggregator collects 
     results to JSON array) enable simple workflows while allowing 
     domain-specific logic injection (e.g., Planner decomposes multi-step 
     workflows, Critic evaluates partial results for consensus). TaskScheduler 
     uses DashMap for lock-free concurrent operations supporting parallel task 
     submission, assignment queries, and state updates from multiple 
     coordinators/workers. The get and subtasks methods enable task status 
     queries and parent-result aggregation. The reset method supports 
     retry-after-failure patterns: failed tasks revert to Pending for 
     reassignment to a different agent. Tests validate the complete lifecycle 
     (Pending→Assigned→Running→Completed preserves input/output), failure 
     handling (error_message captured), retry logic (reset clears assignment), 
     and pluggable traits (decomposer/aggregator contracts). This scheduler 
     forms the foundation for research decision R3's pull-based scheduling where
      workers pull from JetStream queues filtered by task_type and capabilities.
