# Implementation Plan: Phase 4 — Transport & Messaging

**Branch**: `004-phase4-transport-messaging` | **Date**: 2026-03-04 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `/specs/004-phase4-transport-messaging/spec.md`

## Summary

Phase 4 connects the actor system to the outside world through a multi-protocol transport layer. NATS is the primary inter-agent transport — the framework's backbone for pub/sub, request-reply, queue groups, and JetStream durable messaging. HTTP (Axum 0.8) and gRPC (Tonic 0.14) provide external-facing interfaces for management, monitoring, and service mesh deployments. WebSocket support enables real-time event streaming to dashboards and external clients. MCP integration (rmcp 1.1) allows agents to consume external tool servers and expose their own capabilities. All protocols share a unified MessageEnvelope serialized with MessagePack (rmp-serde) for wire transport and JSON for HTTP endpoints.

## Design Decisions

### D1: Transport Trait Design

The `Transport` trait is async with four core operations:

```rust
#[async_trait]
pub trait Transport: Send + Sync + 'static {
    async fn publish(&self, subject: &str, envelope: MessageEnvelope) -> Result<(), TransportError>;
    async fn subscribe(&self, subject: &str) -> Result<Subscription, TransportError>;
    async fn queue_subscribe(&self, subject: &str, queue: &str) -> Result<Subscription, TransportError>;
    async fn request(&self, subject: &str, envelope: MessageEnvelope, timeout: Duration) -> Result<MessageEnvelope, TransportError>;
}
```

`Subscription` wraps an async stream of `ReceivedMessage`. `ReceivedMessage` contains the `MessageEnvelope` plus an optional `reply_subject: Option<String>` carrying the protocol-specific reply address (populated by NATS from the incoming message's reply field, absent in HTTP/gRPC where replies are implicit in the handler return). Responders reply by calling `transport.publish(received.reply_subject.unwrap(), response_envelope)`. This matches async-nats's native pattern (`message.reply: Option<Subject>`) and Erlang/OTP's `gen_server:reply(From, Reply)`. There is no separate `reply` method on the trait because reply mechanisms differ fundamentally across protocols — keeping the trait surface minimal and protocol-agnostic.

### D2: MessageEnvelope Serialization Strategy

Wire format: `rmp_serde::to_vec_named` (MessagePack with named fields for schema evolution). HTTP format: `serde_json`. The envelope struct derives both `Serialize` and `Deserialize`. The `payload` field is `Bytes` — inner message types are serialized separately and placed into the envelope. This avoids double-serialization and allows mixed payload formats.

### D3: InMemoryTransport for Testing

An `InMemoryTransport` implementation backed by `tokio::sync::broadcast` channels enables full Transport trait testing without NATS. This is critical for unit tests and CI environments without Docker.

### D4: Proto File Compilation

Proto files in `specs/004-phase4-transport-messaging/contracts/` are the source of truth. Shared enums and messages live in `common.proto` (imported by service protos) — this prevents duplicate symbol compilation errors and aligns with Constitution Principle I (single source of truth). `tonic-build` in `mister-smith-transport/build.rs` compiles all 4 proto files to Rust types at build time. The generated types are used by both `mister-smith-transport` (message types) and `mister-smith-grpc` (service implementations).

### D5: rmcp Isolation Strategy

`mister-smith-mcp` is the only crate that depends on rmcp. rmcp brings `thiserror ^2` transitively — Cargo handles the coexistence of thiserror 1.x and 2.x in the same dependency tree. At the `mister-smith-mcp` crate boundary, all rmcp error types are wrapped in our own `McpError` type (using thiserror 1.x). No rmcp types leak into the public API of other crates.

### D6: Transport Actors in Supervision Trees

Each transport (NATS, HTTP, gRPC, MCP) runs as a supervised actor within the Phase 3 supervision tree. Connection failures trigger restart policies. The NATS transport is a `Permanent` actor (always restarted). HTTP and gRPC servers are `Permanent` during normal operation. MCP clients are `Transient` (restarted only on abnormal termination).

### D7: WebSocket Event Broadcasting

WebSocket event streaming uses a `tokio::sync::broadcast` channel internally. Agent status changes, task events, and system events are published to the broadcast channel. Each WebSocket connection spawns a task that filters the broadcast stream based on the client's subscription and forwards matching events. This decouples event production from WebSocket connection management.

### D8: Subject Taxonomy Validation

Subject construction is type-safe via `SubjectTaxonomy` builder methods (e.g., `SubjectTaxonomy::agent_command(agent_id, command_type)`). Raw string subjects are validated against known patterns. Invalid subjects are rejected at construction time, not at publish time.

## Complexity Tracking

| Consideration | Justification | Simpler Alternative Rejected |
|---------------|---------------|------------------------------|
| 5 new crates | Each protocol has distinct dependencies (async-nats, axum, tonic, rmcp) that should not cross-pollinate. rmcp isolation requires a separate crate for thiserror conflict. | Monolithic transport crate rejected — would force all consumers to pull in all protocol dependencies. |
| Proto compilation in build.rs | Standard Rust/Tonic pattern for type-safe gRPC. | Hand-written protobuf types rejected — error-prone, no codegen guarantees. |
