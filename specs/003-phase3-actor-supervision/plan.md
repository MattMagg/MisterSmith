# Implementation Plan: Phase 3 — Actor System & Supervision Trees

**Branch**: `003-phase3-actor-supervision` | **Date**: 2026-03-04 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `/specs/003-phase3-actor-supervision/spec.md`

## Summary

Phase 3 implements the actor model and Erlang/OTP-style supervision trees — the framework's core concurrency and fault-tolerance primitives. Two new crates are produced: `mister-smith-actor` (mailbox, ActorRef, ActorSystem) and `mister-smith-supervision` (SupervisionTree, restart policies, failure escalation). Actors process messages sequentially from bounded/unbounded mailboxes, communicate via typed tell/ask patterns, and are organized into hierarchical supervision trees with configurable restart policies and escalation. The implementation integrates with Phase 2's EventBus for lifecycle events and HealthMonitor for observability.

## Design Decisions

### D1: Actor Runtime Model

Each actor runs in its own `tokio::spawn` task with a message processing loop. The loop receives messages from an `mpsc::Receiver`, calls `handle_message` sequentially, and handles lifecycle transitions. This maps directly to the Erlang/OTP model where each actor is a process with a mailbox.

**Why not TaskExecutor?** The async crate's `TaskExecutor` is designed for short-lived tasks with concurrency control. Actors are long-lived tasks that run for the lifetime of the system. Using `tokio::spawn` directly is simpler and avoids unnecessary semaphore overhead.

### D2: ActorRef Type Safety

`ActorRef<M>` is generic over the message type `M`. This provides compile-time type safety — you cannot send an `ActorA::Message` to an `ActorRef<ActorB::Message>`. The `tell` method takes `M`, the `ask` method takes `M` and returns `oneshot::Receiver<Result<R, ActorError>>` where `R` is the response type.

**Ask pattern implementation**: The ask message wraps the user message plus a `oneshot::Sender` for the reply. The actor's `handle_message` returns a value that the actor cell routes back through the oneshot channel.

### D3: Mailbox Design

`Mailbox<M>` wraps `tokio::sync::mpsc::Sender<M>` (bounded) or `tokio::sync::mpsc::UnboundedSender<M>` (unbounded). Default is bounded with capacity 1000 (configurable per actor).

**Mailbox during restart**: Messages in the mailbox are preserved during restart. The mailbox channel persists; only the actor's state is reset. This matches Erlang/OTP behavior where the mailbox survives process restarts. The actor's `pre_start` is called before resuming message processing.

### D4: ActorSystem Owns SupervisionTree

The `ActorSystem` contains an `Arc<SupervisionTree>` and is the entry point for all actor operations. Spawning an actor registers it in both the system's handle registry and the supervision tree. This resolves checklist item CHK030 — ActorSystem owns the tree.

### D5: Supervisors Are Actors

A supervisor is a regular actor whose message type includes supervision commands (child failed, child stopped, etc.). The `SupervisorNode` in the tree holds a reference to the supervisor actor's processing infrastructure. This resolves checklist item CHK031 — supervisors are actors with additional supervision behavior.

### D6: Abnormal Termination Definition

For `RestartScope::Transient`, "abnormal termination" means either:
- `handle_message` returns `Err(...)`
- The actor task panics (caught by the actor cell via `JoinHandle` inspection)

"Normal termination" means the actor's message processing loop ends because:
- The mailbox sender is dropped (no more senders)
- The actor explicitly returns a `Stop` signal

This resolves checklist item CHK028.

### D7: Concurrent Child Failures

When multiple children fail simultaneously, the supervisor processes failures sequentially from its own failure notification channel. Each failure triggers the restart policy independently. For OneForAll/RestForOne, if a restart-all is already in progress and another failure arrives, the in-progress restart completes first, then the new failure is evaluated (the newly restarted child may have already been addressed). This resolves checklist item CHK043.

### D8: ActorSystem Drop Behavior

If `ActorSystem` is dropped without calling `shutdown()`, the `Drop` impl triggers graceful shutdown in a best-effort manner using `tokio::task::block_in_place` (or spawns a shutdown task if already in an async context). All actors receive stop signals, but `post_stop` hooks are called on a best-effort basis. For deterministic shutdown, users MUST call `shutdown().await`. This resolves checklist item CHK046.

### D9: Delivery Guarantees

Tell messages have **at-most-once** delivery semantics. If the mailbox is full (bounded) or the actor is terminated, the message is not delivered and the sender receives an error. No message persistence, retry, or acknowledgment. This matches in-process Erlang semantics and is appropriate for Phase 3's in-process scope. Durable delivery is a Phase 4 transport concern.

### D10: Messages During Restarting State

Messages sent to an actor in `Restarting` state are buffered in the mailbox (which persists across restarts per D3). They are processed after the restart completes and `pre_start` has been called. This resolves checklist item CHK047.

### D11: pre_start Failure on Initial Spawn

If `pre_start` fails during initial spawn (not restart), the actor transitions to `Error` state, the spawn method returns an error, and the actor is not registered in the ActorSystem. If the actor was being spawned as a supervised child, the failure is reported to the parent supervisor as a child start failure. This resolves checklist item CHK045.

### D12: Supervision Tree Depth

No artificial maximum depth limit. Trees are bounded only by available memory and stack depth. Since supervision operations are async and iterative (not recursive), stack overflow is not a concern. This resolves checklist item CHK026.
